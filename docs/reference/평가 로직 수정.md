## **검색 → 생성 단계 평가 추천안**

### 개선 방향

- **`context_recall`을 정답 기준으로 명확화**
    - 기존엔 “컨텍스트가 충분한가”가 추상적이었음.
    - 이제 `ground_truth_answer`를 핵심 사실(`gt_facts`)로 쪼개고, 각 사실이 검색 컨텍스트에 있는지 확인.
    - 구현은 fact별 `is_covered`와 `supported_context_ids`를 남겨 recall을 계산.
- **`context_precision`을 관련도 기준으로 정리**
    - 기존엔 “실제로 사용된 비율”처럼 관측 어려운 정의였음.
    - 이제 상위 컨텍스트 각각을 “질문/정답에 관련 있음 vs 없음”으로 라벨링.
    - 구현은 context별 `is_relevant`를 기록해 불필요 청크 비율을 직접 확인 가능.
- **비율식 점수로 해석 가능성/일관성 강화**
    - 점수를 LLM 감점 감각에 맡기지 않고 코드 공식으로 계산.
    - `context_recall = covered_gt_facts / total_gt_facts`
    - `context_precision = relevant_contexts / total_contexts`
    - 결과적으로 점수 이유를 역추적할 수 있고, 청킹/검색/필터 개선 포인트를 명확히 찾을 수 있음.

한 줄 요약: **충분성(Recall)과 정밀성(Precision)을 둘 다 evidence 기반 + 비율식으로 바꿔서, 점수 신뢰도와 디버깅 가능성을 높인 개선**입니다.

### **목표**

- 검색된 컨텍스트가 **생성에 충분한지/불필요한지**를 안정적으로 평가
- `Context Precision`, `Context Recall`을 “느낌 점수”가 아니라 **근거 기반 점수**로 전환
- 생성 단계 추천안과 동일하게 `evidence`를 남겨 원인 추적 가능하게 운영

### **지표 정의**

- `context_recall`: 정답(`ground_truth_answer`)의 핵심 사실 중, 검색 컨텍스트에 포함된 비율
- `context_precision`: 상위 검색 컨텍스트 중 질문/정답에 실제로 유효한 컨텍스트 비율

### **채점 방식**

- LLM 역할: 구조화 라벨링
    - `gt_facts` 추출 (정답 핵심 사실 목록)
    - 각 fact가 어떤 context에서 커버되는지 매핑
    - 각 context가 관련/비관련인지 라벨링
- 코드 역할: 최종 점수 계산
    - `context_recall = covered_gt_facts / total_gt_facts`
    - `context_precision = relevant_contexts / total_contexts`

### **출력 스키마(검색→생성 전용)**

- 점수 키: `context_precision`, `context_recall`
- 근거 필드: `evidence`
    - `gt_facts[]` (`is_covered`, `supported_context_ids`)
    - `contexts[]` (`is_relevant`, `relevance_reason_short`)
- 선택: `missing_facts[]` (컨텍스트에 없는 정답 사실 목록)

### **구현 원칙 (안전 도입)**

- 기존 `LLMJudge` 유지, `v2` 경로 추가
- 기존 점수 키 유지 + `evidence`만 확장
- 기본 실행 경로는 그대로, 옵션 플래그로만 새 평가 활성화

### **운영 기준**

- `ground_truth_answer`가 없는 샘플은 `context_recall` 계산 제외(정책 명시)
- 컨텍스트 개수 `k` 고정(예: 5 또는 10)해서 실험 비교 가능성 확보
- fact 분해 규칙 고정(숫자/날짜/고유명사 분리, 중복 제거, 최대 항목 수 제한)

### **검증 계획**

- 동일 eval셋 반복 실행 후 점수 분산 확인
- 샘플 수동 점검(10~20문항)으로 `relevant_context` 판정 타당성 검증
- 개선 전후 비교:
    - recall 낮은 문항의 누락 fact가 실제로 검색 미스인지 확인
    - precision 낮은 문항의 불필요 context 비율 확인

### **완료 조건**

- `context_precision`, `context_recall`가 evidence 기반으로 기록됨
- 점수별 근거(`gt_facts` ↔ `contexts` 매핑) 역추적 가능
- 기존 평가/리포트 파이프라인에 영향 없이 병행 운영 가능

## **생성 단계 평가 추천안**

### 개선 방향

- **`answer_correctness` 추가로 정답 확인**
    - 기존 `faithfulness/relevance`는 “근거성/질문적합성” 중심이라 정답 일치를 직접 보지 못했음.
    - `answer_correctness`를 추가해 생성 답변을 `ground_truth_answer`와 직접 비교.
    - 구현은 `ground_truth_answer`를 핵심 사실(`gt_facts`)로 나누고, 답변이 각 사실을 충족했는지 판정해 점수화.
- **근거(evidence) 기반으로 채점해 신뢰도 강화**
    - 점수만 받으면 왜 그 점수인지 추적이 어려움.
    - 각 판정에 근거를 함께 수집:
        - `claims` (답변 주장) + `supported_context_ids`
        - `required_items` (질문 요구항목) + `is_answered`
        - `gt_facts` (정답 사실) + `is_matched`
    - 구현상 Judge 출력 JSON에 이 evidence를 포함하고, 저장 시 `judge_scores.evidence`로 남겨 리뷰 가능하게 함.
- **비율식으로 점수를 명확히 계산**
    - “느낌 점수” 대신 항목 기반 공식 적용으로 일관성 확보.
    - 예:
        - `faithfulness = supported_claims / total_claims`
        - `answer_relevance = answered_items / total_required_items`
        - `answer_correctness = matched_gt_facts / total_gt_facts`
    - 구현은 LLM은 분류(맞음/아님)만 하고, 최종 점수는 코드가 계산해 변동성을 줄임.

이 3개를 같이 적용하면, 한마디로 **“정답성 보강 + 채점 근거 가시화 + 계산 방식 표준화”**로 개선됩니다.

### **목표**

- 생성 평가를 `Faithfulness`, `Answer Relevance`, `Answer Correctness` 3축으로 운영
- 점수만 저장하지 않고, 근거(`evidence`)까지 남겨 재현성과 해석 가능성 확보
- 기존 경로는 유지하고 `v2`를 추가해 안전하게 도입

### **지표 정의**

- `faithfulness`: 생성 답변의 핵심 주장(claim) 중 검색 컨텍스트로 뒷받침되는 비율
- `answer_relevance`: 질문이 요구한 항목(required items)을 답변이 직접 충족한 비율
- `answer_correctness`: 생성 답변이 `ground_truth_answer` 핵심 사실(gt facts)과 일치하는 비율

### **채점 방식**

- LLM 역할: 구조화 라벨링만 수행
    - claim 추출 + support context id
    - required item 추출 + answered 여부
    - gt fact 추출 + matched 여부
- 코드 역할: 최종 점수 계산
    - `faithfulness = supported_claims / total_claims`
    - `answer_relevance = answered_items / total_required_items`
    - `answer_correctness = matched_gt_facts / total_gt_facts`
    - 루브릭형 vs 비율형
        
        ### **1) 순수 루브릭 점수형 (0 / 0.5 / 1.0 직접 채점)**
        
        **개념**
        
        평가자가 답변 전체를 보고 루브릭 기준에 따라 **한 번에 점수 구간**을 줍니다.
        
        **예시 기준**
        
        - `1.0`: 핵심 정보가 정확하고 누락/왜곡 없음
        - `0.5`: 핵심은 맞지만 일부 누락 또는 부분 오류
        - `0.0`: 핵심 오답, 또는 질문 의도와 다름
        
        **장점**
        
        - 사람이 이해하기 쉽고 회의에서 설명이 빠름
        - 복합 문항(비교/요약/거절형)에 유연하게 대응 가능
        
        **단점**
        
        - 채점자(또는 LLM) 주관이 많이 들어가 점수 흔들릴 수 있음
        - 왜 0.5인지 근거가 약하면 팀 합의가 어려움
        
        **언제 쓰면 좋나**
        
        - 초기 PoC
        - 데이터가 적고, 빠르게 품질 감을 볼 때
        - 정량 자동화보다 팀 합의/해석이 더 중요한 단계
        
        ---
        
        ### **2) 루브릭 + 비율형 (항목 판정 후 matched/total 계산)**
        
        **개념**
        
        먼저 루브릭으로 “핵심 사실 리스트”를 만들고,
        
        각 사실을 맞았는지 체크한 뒤 **공식으로 점수**를 냅니다.
        
        `점수 = 맞은 항목 수 / 전체 항목 수`
        
        **예시** 질문 정답 핵심이 4개 사실이라고 하면:
        
        - 4개 다 맞음 → `1.0`
        - 2개 맞음 → `0.5`
        - 0개 맞음 → `0.0`
        
        **장점**
        
        - 재현성 높음(누가 채점해도 비슷)
        - 왜 이 점수인지 역추적 쉬움(항목별 로그가 남음)
        - 모델 비교/실험 추세 분석에 유리
        
        **단점**
        
        - 초기 설계(핵심 사실 분해 규칙) 작업이 필요
        - 너무 기계적으로 설계하면 문맥 품질을 놓칠 수 있음
        
        **언제 쓰면 좋나**
        
        - 팀 운영 평가(주간/월간 리포트)
        - 모델/프롬프트/청킹 개선 효과를 정량 비교할 때
        - “점수 근거를 요구받는” 협업 환경
        
        ---
        
        ## **한 문장 비유 (설명용)**
        
        - **순수 루브릭형** = “채점자가 답안지를 읽고 총평 점수 주는 방식”
        - **루브릭+비율형** = “문항별 정오표로 채점해서 자동 합산하는 방식”
        - 비율형 실행 방법
            
            ## **방법 1) LLM이 `ground_truth_answer`를 사실 항목으로 분해 (가장 현실적)**
            
            - 입력: `ground_truth_answer`
            - 출력: `gt_facts = [fact1, fact2, ...]` (원자적 사실 리스트)
            - 그 다음 생성답이 각 fact를 충족했는지 체크
            
            예:
            
            - GT: “예산 3.52억, 1차 오픈 7/10, 2차 오픈 9월”
            - 항목 3개로 분해 → 맞은 개수/3
            
            이 방식이 지금 데이터셋에서 제일 바로 적용 가능해요.
            
            ## **방법 2) 규칙 기반 분해 (안정적, 구축비용 있음)**
            
            질문 타입(A/B/D/E 등)별로 정해진 슬롯을 강제로 만듭니다.
            
            - A(단일 사실): 금액/날짜/기간 같은 1~2 슬롯
            - B(비교형): 대상별 값 + 정렬/최대최소
            - D(거절형): “문서 내 없음” 판단 + 환각 금지
            - E(오타형): 의도복원 + 핵심사실
            
            이건 일관성은 높지만 초기 룰 설계가 필요합니다.
            
            ---
            
            ## **그래서 “라벨링 없는 지금” 추천**
            
            1. **1차**: LLM 분해 방식으로 시작
            2. **안정화**: 분해 규칙 가이드(원자성 규칙) 추가
            3. **중요 문항만** 수동 라벨링해서 검증셋 운영
            
            ---
            
            ## **항목 카운팅 규칙(꼭 고정해야 함)**
            
            - 사실 1개는 **하나의 검증 가능한 주장**만 포함
            - “그리고/또한”으로 묶인 문장은 분할
            - 숫자·날짜·고유명사는 별도 항목으로 분리
            - 중복 사실 제거
            - 항목 수 상한(예: 6개) 설정해 과분해 방지
            
            이렇게 하면 라벨셋이 없어도 `맞은 항목 수 / 전체 항목 수`를 운영 가능한 수준으로 돌릴 수 있습니다.
            

### **출력 스키마(생성 평가 전용)**

- 기존 점수 키 유지: `faithfulness`, `answer_relevance`
- 신규 점수 키 추가: `answer_correctness`
- 근거 필드 추가: `evidence`
    - `claims[]`, `required_items[]`, `gt_facts[]`, 각 항목의 매핑 id 포함

### **구현 원칙 (안전 도입)**

- 기존 `LLMJudge`는 그대로 둠
- `LLMJudgeV2`를 추가하고 CLI 플래그로 선택 실행
- `judge_scores`에 신규 필드만 확장(기존 소비 코드 호환 유지)

### **운영 기준**

- `ground_truth_answer`가 있는 샘플만 correctness 계산
- D유형(거절형)은 “문서 내 정보 없음” 판단 정확도를 correctness에 반영
- 파싱 실패/필드 누락 시 기존처럼 에러 기록 + 해당 항목 점수 0 처리(또는 샘플 제외 정책 명시)

### **검증 계획**

- 동일 eval셋 2~3회 반복 실행하여 점수 분산 비교
- 기존 judge 대비:
    - 평균 점수 변화
    - 샘플별 편차
    - 파싱 실패율
- 표본 수동검토(10~20문항)로 correctness 체감 일치 확인

### **완료 조건**

- 생성 평가 3지표가 모두 기록됨
- 각 점수에 대응하는 `evidence`가 저장됨
- 기존 평가 커맨드/리포트가 깨지지 않음
- 팀원이 샘플 단위로 “왜 이 점수인지” 역추적 가능

## **검색 → 생성 단계: 점수 기반 개선 가이드**

| **평가지표** | **점수 패턴** | **의미 해석** | **우선 점검할 파이프라인** |
| --- | --- | --- | --- |
| `context_recall` 낮음, `context_precision` 보통/높음 | 필요한 정보가 top-k에 충분히 안 올라옴 | 정답 사실 누락형 검색 | 리트리버 `k`, 쿼리 리라이팅, 메타필터 조건 완화, 하이브리드 검색(BM25+벡터), 리랭커 |
| `context_recall` 높음, `context_precision` 낮음 | 필요한 정보는 있지만 잡음 청크가 많음 | 과다검색/정밀도 부족 | 리랭커 도입, top-k 축소, 섹션 필터 강화, 도메인/기관 필터 정교화 |
| 둘 다 낮음 | 문서 선택/청크 선택 모두 부정확 | 검색 체계 전반 문제 | 임베딩 모델/인덱스 재검토, 청킹 경계/크기 재설계, 메타데이터 품질 점검 |
| 둘 다 높음인데 생성 점수가 낮음 | 컨텍스트는 충분한데 답변 생성이 실패 | 생성 단계 문제 | 시스템 프롬프트, 답변 포맷 가이드, 인용 강제, 디코딩/모델 파라미터 |
| `missing_facts`가 특정 타입(숫자/날짜/표)에 집중 | 특정 정보 형태를 검색이 잘 못 올림 | 표/정형정보 취약 | 표 청킹 규칙, 표 우선 부스팅, 숫자/날짜 포함 청크 가중치 |

## **생성 단계: 점수 기반 개선 가이드**

| **평가지표** | **점수 패턴** | **의미 해석** | **우선 점검할 파이프라인** |
| --- | --- | --- | --- |
| `faithfulness` 낮음, `context_recall` 높음 | 근거는 있는데 답변이 벗어남(환각/오조합) | 생성기 근거 사용 실패 | 생성 프롬프트에 “근거 없는 주장 금지”, 출처 인용 강제, 긴 답변 억제 |
| `answer_relevance` 낮음, `answer_correctness` 보통/높음 | 맞는 말을 하지만 질문 요구를 덜 충족 | 질문 파싱/응답 구조 문제 | 질문 슬롯 추출 강화, 답변 템플릿(요구항목별), 누락 항목 체크 단계 |
| `answer_correctness` 낮음, `faithfulness` 높음 | 근거는 따르지만 정답과 불일치(부분답/해석오류) | 정답 커버리지 부족 | 정답 사실 커버 지시 강화, 다중 사실 질문 분해, 비교/정렬 지시 보강 |
| `answer_correctness` 낮음 + `context_recall` 낮음 | 정답 불일치 원인이 검색 누락 | 생성보다 검색 우선 수정 | 검색→생성 단계(리트리벌/리랭크/청킹) 먼저 개선 |
| `answer_relevance`·`correctness` 모두 낮음 (E형 오타 질의 집중) | 의도 복원 실패 | 질의 정규화 취약 | 오타 교정/동의어 확장, 질의 전처리, 기관명/사업명 normalization |
| D형(거절형)에서 `faithfulness` 낮음 | 문서에 없는데 지어냄 | 거절 정책 미흡 | “없으면 없다” 규칙 강화, 민감정보 질의 거절 템플릿, 반례 few-shot |

## **실무 운영 팁 (짧게)**

- **검색→생성 먼저, 생성 다음** 순서로 보세요.(`context_recall/precision`이 낮으면 생성 점수는 따라 내려갑니다.)
- 개선 우선순위는 보통
    1. `context_recall`
    2. `faithfulness`
    3. `answer_correctness`
    4. `answer_relevance`순으로 잡는 게 효율적입니다.
- 각 점수는 반드시 `evidence`와 같이 봐야 정확한 원인 분해가 됩니다.
