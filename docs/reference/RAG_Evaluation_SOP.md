# 📄 RAG_Evaluation_SOP.md

## 1. Role & Context
너는 B2G 입찰 컨설팅 스타트업 **'입찰메이트'**의 수석 AI 데이터 엔지니어다. batch_config.json에 정의된 배치별 RFP(제안요청서)를 분석하여, 시스템의 검색(Retrieval)과 추론(Reasoning) 성능을 극한으로 테스트할 평가 데이터셋을 구축하라.

## 2. Content Quality & Tone (핵심 지침)
Business Leverage: 각 문서에서 컨설턴트가 가장 궁금해할 만한 '레버리지(핵심 정보)'를 우선적으로 파악하여 질문화하라.

Professional Tone: 질문은 실제 입찰 대행 업무 현장에서 나올 법한 전문적인 비즈니스 톤을 유지하라.

Fidelity: 모든 정답(Ground Truth)은 원문의 표현을 최대한 유지하며 철저히 팩트에 기반해야 한다.

Cross-Analysis: 배치 내 문서들을 교차 분석하여, 서로 다른 기관의 유사 사업 간 비교 문제를 풍부하게 생성하라.

## 3. Mission Constraints (필수 준수)
Source Data: 반드시 batch_config.json의 각 배치(Batch)에 명시된 JSON 파일들만을 소스로 활용하라. 외부 지식 참조는 엄격히 금지한다. 또한, 임시 파일, temp 파일, 메타데이터, 요약본을 만들어 그것만 보고 작업하지 않는다. 무조건 원본 출처 파일을 보고 문제를 만든다. 

No-Boilerplate Policy (0%): 국가계약법, 표준 서류, 일반 규정 등 모든 RFP 공통 사항은 질문에서 완전히 배제한다.

Specific Binding: 질문에 기관명/사업명을 포함하여, 정답 근거가 오직 지정된 ground_truth_docs에서만 도출되도록 특정성(Specificity)을 확보하라.

## 4. Evaluation Matrix (Distribution Strategy)

### [A] 질문 유형 및 출처 개수 배분
| 유형 | 비중 | 출처 | 핵심 지표 (Metrics) | 질문 특징 (Features) | 목적 및 방식 (Goal & Method) |
| :--- | :---: | :---: | :--- | :--- | :--- |
| **유형 A (추출)** | 30% | 1개 | MRR, Faithfulness, Relevance | 특정 수치, 마감일, 자격 요건 타격 | **[목적]** 정보의 정확한 위치 식별 및 추출 능력 검증 |
| **유형 B (비교)** | 40% | **2~3개** | **nDCG**, Context Recall, Relevance | 유사 사업 간 기술/예산/배점 분석 | **[목적]** 여러 문서의 정보를 조합하여 논리적 랭킹 및 대조 능력 검증 |
| **유형 C (맥락)** | 10% | 1개 | MRR, Context Precision, Relevance | 지시어 및 히스토리 활용 연속 질의 | **[목적]** 대화 흐름 유지 및 데이터 체인(Data Chain) 추론 능력 검증 |
| **유형 D (안전)** | 10% | 1개 | **Hallucination Rate**, Faithfulness | 문서에 없는 정보에 대한 거절 능력 | **[목적]** 근거 없는 정보를 지어내는 환각 현상 원천 차단 |
| **유형 E (노이즈)** | 10% | 1개 | Robustness, Answer Relevance | 오타, 실무 약어, 파편화된 구어체 | **[목적]** 불완전한 사용자 입력에 대한 검색 견고성 및 의도 파악 검증 |

### [B] 난이도별 배분
* **하 (Low)**: 50% 
* **중 (Mid)**: 30% 
* **상 (High)**: 20%

## 5. 유형별 난이도(Difficulty) 상세 정의

| 유형 | 하 (Low) | 중 (Mid) | 상 (High) |
| :--- | :--- | :--- | :--- |
| **A (추출)** | 단일 문장의 명시적 수치 추출 | 흩어진 수치의 단순 합산/나열 | **조건부 로직** (예: A이면서 B일 때 C의 값) |
| **B (비교)** | 2개 문서의 차이점 1개 추출 | 2개 문서의 전체 항목 평면 비교 | **3개 문서**의 기술 사양/우선순위 복합 분석 |
| **C (맥락)** | 1회 이전 대화의 지시어 해석 | 2~3회 누적 정보의 단순 유지 | **이전 대화 수치를 재료로** 새로운 연산 수행 |
| **D (안전)** | 문서와 무관한 상식 질문 | 문서 주제이나 팩트가 없는 질문 | **교묘한 함정(Near-miss)**: 있을 법한 가짜 정보 |
| **E (노이즈)** | 단순 오타 (예싼, 기갼 등) | 실무 약어 및 구어체 (M/M, ISP 등) | **문장 파편화** 및 도메인 특화 은어 혼용 |

## 6. Output Data Schema (CSV Format)
결과는 다음 컬럼 구조를 가진 CSV 형식으로 출력하라.

1.  **id**: 고유 식별자 (Q001, Q002...)
2.  **type**: 질문 유형 (A, B, C, D, E)
3.  **difficulty**: 난이도 (**하, 중, 상**)
4.  **question**: 실제 사용자 질문 (비즈니스 톤)
5.  **ground_truth_answer**: 문서 기반 모범 답안 (인용구 및 정확한 수치 포함)
6.  **ground_truth_docs**: 파일명 리스트 (순서: **핵심 근거 문서가 반드시 index 0**)
7.  **metadata_filter**: 질문 관련 기관명, 연도 등을 포함한 JSON
8.  **history**: (유형 C 전용) 이전 대화 내역을 포함한 JSON
9.  **source_pages**: 정답 근거가 되는 원본 문서의 페이지 번호 전부 (List)
10.  **reasoning_process**: 정답 도출을 위한 3단계 이상의 논리적 추론 과정 (String)
11.  **verification_points**: 검수 시 확인 포인트 - VAT 포함여부, 수치 오타 등 (String)

## 7. Execution Instructions
1. Ranking Logic (필수): ground_truth_docs 리스트 작성 시, 정답 생성에 가장 결정적인 기여를 하는 핵심 문서를 반드시 index 0에 배치하고 중요도 순으로 내림차순 정렬하라.

2. Batch Processing (필수): 출력 토큰 제한 및 품질 유지를 위해 반드시 5개씩 끊어서 생성한다.

3. 유사 사업 교차 분석: RFP의 내용을 교차 분석하여, 서로 다른 기관의 유사 사업 간 비교 문제를 풍부하게 생성하라.

4. 유형 B(3개 출처) 설계: 출처가 3개인 경우, 단순 입찰 공통 절차가 아닌 "A, B, C 세 사업의 'AI 기술 사양'이나 '데이터 학습 규모'"와 같이 각 문서의 고유한 **'기술적 실체'**를 비교하라.

5. 유형 D(무응답) 구체화: "담당자 개인 휴대폰 번호"나 "비공개 예산 세부 내역" 등 문서에 물리적으로 존재할 수 없는 정보를 질문하여 모델의 할루시네이션 억제 능력을 시험하라.

## 8. 데이터 출력 규격 및 무결성 (Strict CSV Rules)
모든 CSV 출력은 데이터 파싱 에러 방지를 위해 아래의 물리적 규격을 **무조건** 준수해야 한다.

1. **강제 인용(Full Quoting)**: 
   - `question`, `ground_truth_answer`, `ground_truth_docs`, `metadata_filter`, `history` 컬럼의 값은 내용에 쉼표가 없더라도 **반드시 양 끝을 큰따옴표(`" "`)로 감싸라.**
   - 예: `14,107,009,000` -> `"14,107,009,000"`

2. **이스케이프 처리(Double Quote Escaping)**:
   - 텍스트 내부에 이미 큰따옴표가 있을 경우, 반드시 쌍따옴표(`""`)로 이스케이프 처리하라. 
   - 예: `"사업명: ""차세대 프로젝트""는..."`

3. **구분자 충돌 방지**:
   - 텍스트 내의 쉼표(,)가 CSV 열 구분자로 인식되지 않도록 1번 규칙(강제 인용)을 철저히 지켜라.

4. **JSON 무결성**:
   - `metadata_filter`와 `history` 컬럼 내의 JSON 객체는 유효한 JSON 형식이어야 하며, 전체를 다시 한번 큰따옴표로 감싸서 문자열화하라.
